# mcpOGV — MCP-сервер Directum RX для ИИ-ассистентов органа власти

Версия описания: 14.10.2026. Ветка `feature/mcp-ogv`.

mcpOGV даёт LLM-агентам (LibreChat и любым MCP-клиентам) доступ к Directum RX: чтение заданий, поручений, документов,
обращений граждан, правовых актов, контроля исполнения — и, если включено, создание документов и задач. Предметная
логика (59-ФЗ, ТОТК, дерево поручений, права, отсечение персональных данных) реализована на сервере, а порядок работы
для типовых задач — в навыках агента.

## 1. Архитектура и режимы работы

```
LibreChat (агенты, навыки, среда выполнения кода)
        │  MCP Streamable HTTP, заголовок X-MCP-Key
        ▼
mcpOGV (Python, FastAPI + MCP, порт 8010)
        │  OData сервиса интеграции RX (/Integration/odata), Basic-авторизация
        ▼
Directum RX (стенд governmentgenai.directum360.ru)
```

| Аспект | Как устроено |
|---|---|
| Транспорт | MCP Streamable HTTP, `http://<хост>:8010/mcp`; `/health` — проверка живости |
| Доступ к серверу | Общий секрет LibreChat ↔ mcpOGV в заголовке `X-MCP-Key` |
| Учётная запись RX | **Личная**: LibreChat передаёт `X-Directum-Login` / `X-Directum-Password` — ответы ровно в правах пользователя. **Служебная** (`MCP_ALLOW_ENV_CREDENTIALS=true`, сейчас Administrator на стенде): все запросы от неё, `get_current_user` возвращает `service_account=true` |
| Профили учёток | `MCP_ACCOUNTS_FILE` — JSON `{"имя": {"login", "password"}}` вне репозитория; подключение mcpOGV в `librechat.yaml` передаёт `X-MCP-Account: имя` (см. `docs/mcp-ogv/librechat.example.yaml`). Учётку закрепляет подключение у агента, модель её не выбирает; неизвестный профиль — ошибка. Порядок: личные креды → профиль → служебная учётка |
| Запись в RX | Выключена по умолчанию; `MCP_WRITE_ENABLED=true` регистрирует тулы создания. Все записи — в два шага (предпросмотр → `confirm_token`) и в журнал `mcp_writes.log` |
| Часовой пояс | `MCP_UTC_OFFSET` (стенд +04:00) — границы «сегодня», «на неделе», сроки |
| Ссылки | Каждый объект в ответах несёт `url` карточки веб-клиента RX |
| Персональные данные | Тулы обращений не запрашивают адрес, телефон, email, ПИН заявителей |

**Режим служебной учётки — важно.** Под Administrator «я / мои / me» означает служебную учётку, права RX выдачу не
ограничивают. Тулы с «me» под служебной учёткой возвращают понятную ошибку; агент спрашивает ФИО пользователя и
передаёт его явно. Записи делаются от имени служебной учётки (поле «Автор» в RX), реальный человек указывается в
«Подготовил» / «Выдал» / «Автор задачи» (параметр `on_behalf_of`) и в примечании документа.

## 2. Тулы

Обозначения: **Ч** — только чтение, **З** — запись (видны при `MCP_WRITE_ENABLED=true`, всегда два шага).

### 2.7. Создание в RX (запись)

Все тулы: два шага (без `confirm_token` — предпросмотр плана с найденными id и токен; с токеном — создание),
обязательный `on_behalf_of` (реальный сотрудник), журнал аудита. Исполнителям работа назначается только действующим
сотрудникам; от имени закрытого — допускается с пометкой.

| Тул | | Что делает | Задачи |
|---|---|---|---|
| `create_document` | З | Документ любого из 8 типов (исходящее/входящее письмо, служебная записка, приказ, распоряжение, простой документ, приложение, правовой акт): вид, реквизиты, простые поля, тело из текста/markdown или по шаблону RX | Подготовить письмо, записку, приказ |
| `create_outgoing_letter` | З | Упрощённое исходящее письмо | Сопроводительное, запрос в ведомство |
| `create_legal_act` | З | Проект правового акта / акт | Проект НПА (см. ограничение «Категория») |
| `create_document_body` | З | Новая версия документа из текста или markdown | Новая редакция |
| `create_document_body_base64` | З | Новая версия из файла: `content_base64` или `upload_id` после загрузки частями | Перенос файла |
| `begin_upload` / `upload_chunk` / `commit_upload` | З | Загрузка файла до 20 МБ частями в память mcpOGV (в RX ничего не пишется); `commit_upload` собирает и даёт `sha256` | Файл не помещается в один вызов |
| `create_action_item` | З | Поручение по документу с «Выдал», соисполнителем, контролем, документом во вложениях; запуск | Выдать поручение |
| `create_action_items` | З | Пакет поручений (до 20) одним подтверждением | Вся резолюция из `kd-resolution` |
| `send_document_for_review` | З | Документ на рассмотрение руководителю | Передать входящее с проектом резолюции |
| `send_document_for_approval` | З | Документ на согласование по регламенту RX | Согласование письма, проекта |
| `create_task` | З | Простая задача исполнителям с документами | Поручить без документа-основания |
| `request_action_item_report` | З | «Запросить отчёт» по поручению (простой задачей, см. раздел 3); только выдавший или контролёр | Контролёр запрашивает статус |

## 3. Ограничения и наблюдения API Directum RX

Собраны при разработке и живых проверках на стенде. Ячейка «Решение» — как это обработано в mcpOGV.

### 3.1. Протокол и данные

| Наблюдение | Решение |
|---|---|
| IIS отклоняет «+» в пути функции OData (`…/Func(date=…+04:00)` → 404) | Даты в путях функций — в UTC с `Z` |
| Часть наборов требует `$filter` («слишком широкий запрос») | Курируемые тулы всегда фильтруют; `odata_query` требует filter |
| Тело версии — только через `…/Body/$value`; без `$value` — 404 | Чтение тела по `…/Body/$value` |
| Файлы версий бывают потеряны в хранилище (500); расширение в карточке бывает неверным (docx помечен как pdf) | Запасной путь через `PublicBody`; формат определяется по содержимому |
| Ошибки валидации сохранения приходят JSON-строкой («Не заполнено обязательное свойство …») | Текст ошибки передаётся агенту дословно с подсказкой |
| Номера задач и заданий пересекаются (задание 1078 ≠ задача 1078) | Параметр `entity_type`, поле `task_id` |
| Нет запроса полнотекстового поиска (только индексация `IndexDocumentsForFullTextSearch`) | `find_documents_by_content`: кандидаты + чтение текстов + ранжирование |
| RAG (QASearch) асинхронный, кратковременные сбои «RAG service request failed»; ищет только по документам в областях | Повтор запуска; области документов используются автоматически, если проиндексированы |
| Классификатор ТОТК: в RX `Topic` = тематика (2-й уровень), `Theme` = тема (3-й) | Уровни в тулах и промптах — по ТОТК |
| Сроки обращений в RX уже рассчитаны в календарных днях (`Deadline`, `InitialDeadline`) | Не пересчитываются; рабочие дни — только для внутренних сроков |
| Ответные письма: строки `Requests` (обращение + вопрос + результат) есть не у всех; у старых — только одиночное поле `Request` | Запасной путь через вопросы самого обращения |
| Встроенные тулы RX (`drx_native_*`) меняются от версии к версии (7 → 6) | Проксируются динамически |
| Связи документов читаются функциями `DocumentProcessing/GetDocumentRelations`, `GetDocumentsRelations`, `GetRelationTypes` (добавлены по требованиям `docs/rx-integration-requirements.md`). Документ без связей — 204; ненайденный Id — 400; в пакете один ненайденный Id роняет весь запрос | Тулы `get_document_relations`, `list_relation_types`; 204 — пустой список, ненайденные Id убираются из пакета с повтором. На стенде без функций `get_legal_act` откатывается на подбор по названию с пометкой |
| Номер правового акта повторяется по годам («001/26» от 19.01 и от 14.10) | Принятый акт ищется по `ProjectId`, номер — только вместе с датой |

### 3.2. Создание документов и задач

| Наблюдение | Решение |
|---|---|
| Наборы базовых типов абстрактны: POST в `ILegalActsLegalDocumentBases` → 404 с пустым телом | Создание в конкретном наборе (`ILegalActsLegalActs`) |
| **Правовой акт: обязательное поле «Категория» не опубликовано в сервисе интеграции** — проект НПА через API не создаётся | Понятное сообщение; агент готовит текст для ручного создания. **Нужно опубликовать поле в RX** |
| Исходящему письму обязательны вид, «Подготовил», подразделение, наша организация, корреспондент | Подразделение и организация берутся из карточки «Подготовил» |
| Простому документу и приложению RX не формирует «Имя» сам | «Имя» = тема |
| Служебная записка: у вида включена автонумерация без настройки нумерации | Настройка RX (администратор) |
| Согласование не запускается: «нет подходящей настройки регистрации» | Настройка RX (правила регистрации для вида документа) |
| `RecordManagement/CreateActionItemExecution` берёт «Выдал» из карточки текущего сотрудника — у служебной учётки её нет | Поручение собирается напрямую: `IActionItemExecutionTasks` + `CoAssignees` + `Texts` + `AttachmentDetails` + `StartTask` |
| Текст поручения (`ActionItem`) — производное поле: правка не меняет его, текст берётся из `Texts` | Текст — через `Texts` |
| Документ во вложения задачи — через `AttachmentDetails` (группа «Документы», GUID типа из вида документа) | Используется при создании поручений |
| Штатная задача «Запрос отчёта» (`IStatusReportRequestTasks`) через OData — 500 при любом наборе полей | Запрос — простой задачей «Запрос отчета по поручению № …»; ответы видны в досье |
| `Shell/AbortTask` прекращает простые задачи, но «не находит» поручения и задачи рассмотрения | Тестовые задачи прекращаются вручную в RX |
| Черновики задач удаляются DELETE; правка «Автор»/«Выдал» в черновике до старта работает | Используется для задач рассмотрения, согласования, простых |
| Права на документ, созданный служебной учёткой, сотруднику не выдаются автоматически | `GrantAccessRightsToDocument` при заданном `MCP_WRITE_GRANT_RIGHTS_GUID` (GUID типа прав — у администратора RX) |

### 3.3. Учётные записи и права

| Наблюдение | Решение |
|---|---|
| У Administrator нет карточки сотрудника; «текущий пользователь» — не человек из чата | Флаг `service_account`, «me» запрещено, `on_behalf_of` обязателен |
| Закрытые (уволенные) сотрудники остаются авторами и контролёрами старых поручений, а поиск только по активным подтягивал посторонних | Поиск закрытых по полному ФИО со статусом |
| Под служебной учёткой права RX не ограничивают выдачу | Правила в промптах «показывай только нужное»; для продуктивной работы — личные учётки |

### 3.4. LibreChat

| Наблюдение | Решение |
|---|---|
| Фигурные скобки в инструкциях агента ломают промпт | Промпты и SKILL.md без фигурных скобок |
| После перезапуска mcpOGV LibreChat может показывать «сервер не предоставил инструментов» (кэш) | Переинициализировать MCP-сервер; при необходимости перезапустить LibreChat |
| Новые тулы не появляются у агента сами | Отметить тулы у агента, начать новый чат |
| Субагенты требуют capability `subagents` в `librechat.yaml` и настройки агента | См. раздел 5 |
| Чтение текста документа — 2–3 с; длинные выборки | Тулы со страницами (`next_skip`) и лимитами |

### 3.5. Что нужно от администратора RX

1. Опубликовать в сервисе интеграции поле «Категория» правового акта — для создания проектов НПА.
2. Дать GUID типа прав для выдачи доступа на созданные документы (`MCP_WRITE_GRANT_RIGHTS_GUID`).
3. Настроить нумерацию для вида «Служебная записка» и регистрацию для видов, которые отправляют на согласование.
4. Создать и проиндексировать RAG-область «Документы» по нужным документам — для смыслового поиска по содержанию.
5. Для продуктивного режима — передавать в mcpOGV личные учётные данные пользователей или служебную учётку с карточкой
   сотрудника.

## 5. Рекомендуемая настройка агентов

Четыре агента: главный и три профильных. Промпты — `docs/prompts/*.md` (вставлять текст между
«НАЧАЛО ПРОМПТА» и «КОНЕЦ ПРОМПТА»). Модель — с вызовом инструментов; для навыков со скриптами — включённая среда
выполнения кода (Python 3.10+).

### 5.1. Общие настройки LibreChat

- MCP-сервер mcpOGV: `type: streamable-http`, `url: http://<хост>:8010/mcp`, заголовок `X-MCP-Key`. Для личного режима —
  пользовательские переменные с логином и паролем RX в заголовках `X-Directum-Login` / `X-Directum-Password`.
- Субагенты и передача разговора: capability `subagents` (и, если используется, `handoffs`) в разделе
  `endpoints.agents.capabilities` файла `librechat.yaml` — явный список заменяет значения по умолчанию, перечислите все
  нужные возможности; у главного агента — «Дополнительные настройки» → Subagents → профильные агенты; профильные агенты
  должны быть доступны (расшарены) пользователям.
- После обновления mcpOGV: переинициализировать сервер, отметить новые тулы, начать новый чат.

### 5.2. Главный агент — `main-agent.md` (или `main-agent-compact.md`)

| | |
|---|---|
| Роль | Ассистент сотрудника: мои дела, документы, разовые вопросы по всем доменам; сложное — профильным агентам |
| Тулы | Все курируемые тулы чтения; при включённой записи — все тулы создания; `odata_*` по желанию |
| Навыки | `pdf-report`, `excel-report`, `pdf-read` |
| Предметная часть | Служебная учётка и «я»; персональные данные; поиск по содержанию — один вызов; делегирование профильным агентам |

| | |
|---|---|
| Роль | Регистраторы, исполнители, руководитель УРОГ |
| Тулы | `get_citizen_request_status`, `list_citizen_requests_due`, `get_citizen_requests_analytics`, `search_citizen_request_classifier`, `list_citizen_request_answers`, `get_document_text`, `find_documents`, `find_documents_by_content`, `get_template_body_md`, `ask_documents`, `list_employee_action_items`, `get_action_item`, `get_department_discipline`, `search_employees`, `get_current_user`, `add_working_days`; запись — `create_outgoing_letter`, `create_document`, `create_action_item`, `send_document_for_review` |

| Предметная часть | 59-ФЗ (3 / 7 / 30 / +30 / 60 дней, ст. 11), ТОТК, обращения ≠ вопросы, персональные данные заявителей, ответ заявителю — только из карточки обращения в RX |

### 5.4. «Правовой отдел — НПА» — `legal-acts-agent.md`

| | |
|---|---|
| Роль | Юристы и руководитель правового отдела |

| Навыки | `pa-route`, `pa-legal-basis`, `pa-normcontrol`, `pa-anticorruption`, `pa-orv`, `pa-compare`, `pa-conclusions`, `pdf-report`, `excel-report`, `pdf-read` |
| Предметная часть | Проект ≠ принятый акт; законодательство — только из ГАРАНТа; анализ ≠ экспертиза; ограничение «Категория» при создании проекта |

| | |
|---|---|
| Роль | Контролёры, помощники руководителя |
| Тулы | `list_controlled_action_items`, `get_control_dossier`, `get_resolution_history`, `get_document`, `get_document_text`, `find_documents`, `list_employee_action_items`, `get_department_discipline`, `search_employees`, `get_current_user`, `add_working_days`; запись — `create_action_items`, `create_action_item`, `send_document_for_review`, `request_action_item_report` |
| Навыки | `kd-monitor`, `kd-dossier`, `kd-close`, `kd-resolution`, `pdf-report`, `excel-report`, `pdf-read` |
| Предметная часть | Контроль — это поручение с признаком «На контроле», не карточка; прогноз — не оценка людей; по существу — только по тексту отчёта; запрос отчёта — от выдавшего или контролёра |

### 5.6. Общие правила для всех агентов (уже в промптах)

- Только факты из инструментов; всегда ссылка на карточку; сначала инструмент, потом ответ.
- В начале — `get_current_user`; под служебной учёткой — спросить ФИО и не использовать «мои» тулы.
- Создание — предпросмотр → явное «да» → `confirm_token`; `on_behalf_of` — реальный человек; регистрацию, подписание и
  отправку делает сотрудник в RX.
- Ошибку тула пересказать простыми словами и не повторять тот же вызов.

|---|---|

| Упаковка навыков | `python docs/usecases/skills/package_skills.py` → `dist/` (проверка требований платформы: YAML-заголовок, ≤ 50 МБ) |
