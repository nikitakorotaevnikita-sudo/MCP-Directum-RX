# Новые агенты и навыки mcpOGV / Cowork — генерация и приоритеты

Дата: 20.11.2026. Ветка `feature/mcp-ogv`.

Источники:

- решения Directum для госорганов (directum.ru/solutions/industries/government):
  - Делопроизводство: ИИ-распознавание реквизитов, проект резолюции — MVP;
  - Обращения граждан: ИИ-классификация, журнал, исполнитель;
  - НПА;
  - МЭДО;
- пилоты в органах власти: Мособласть, Аппарат Правительства РФ:
  - краткое содержание документов, похожие документы, история документа;
  - далее — проекты резолюций и черновики ответов;
  - решение всегда за человеком;
- заметки по ОГ: номенклатура дел, поиск подобных, маршрутизатор;
- что уже есть у нас — `docs/skills/README.md`.

Что уже закрыто — в генерацию не попадало:

- **Документы и отчёты:** pdf/excel/pptx-отчёты, чтение PDF и Excel, новая версия документа;
- **Агенты:** обращения граждан (`og-*`), правовой отдел (`pa-*`), контроль исполнения (`kd-*`);
- **Class OG:** классификатор и ответы на обращения.

## Как приоритизировали

Ценность для заказчика оценивалась по трём признакам:

- частота задачи;
- сэкономленное время сотрудника;
- видимость для руководителя.

Её взвешивали против готовности:

- есть ли нужные тулы mcpOGV;
- нужны ли правила от заказчика;
- риск ошибки.

Итог по шкале:

- **P1** — делать сейчас;
- **P2** — следующая итерация;
- **P3** — по запросу.

|---|---|---|---|---|---|
| 1 | `doc-summary` | Выжимка документа или пакета по единой форме: суть, что требуется от адресата, сроки, ответственные, связанные документы. Длинный текст — частями, с номерами страниц | Самый частый запрос руководителя и помощника; проверено пилотами Мособласти и АП РФ | Тулы есть: `get_document_text`, `get_document_relations` | **P1** |

| 5 | `ocr-scan` | Текст из сканов без текстового слоя (`pdf-read` их только находит) | Входящие из почты и приёмной часто сканы — без OCR остальные навыки слепы | Нужен OCR в среде выполнения кода (tesseract-rus) или функция распознавания RX | **P3** |

| 1 | **«Маршрутизатор входящих»** (см. п. 3.3) | Вид маршрута для входящего: на рассмотрение (адресат по вопросу), на исполнение, в дело; предполагаемые исполнители; проект резолюции | `route-review`, `route-execution`, `route-to-file`, `kd-resolution` | правила маршрутизации; помещение в дело | Directum заявляет: регистрация быстрее на 35–50%, точность определения исполнителя — 90% (Владимирская обл.) | **P1** |

| 5 | **«Сводный ответ»** | Входящий запрос ведомства с несколькими соисполнителями: сроки, кто ответил, чего не хватает, сводный ответ из отчётов соисполнителей, сопроводительное | `answer-assembly`, `doc-summary`, `docx-builder` | — (отчёты по поручениям через `get_control_dossier`) | Межведомственная переписка — постоянный источник просрочек | **P3** |

Не взяты: кадры (HR Pro на паузе), МЭДО/ПОС-операции (их делает сам RX), закупки (нет в решении для ОГВ).

## 3. Итоги генерации по ОГ (из заметок)

### 3.1. Номенклатура дел для входящего обращения — агент «Делопроизводитель»

- **Запуск.** Запрос идёт со стороны RX: блок процесса вызывает агента Cowork. Это та же схема, что «Запросы из процессов RX» с `task_id`.
- **Работа агента:**
  1. Определяет, к какой **НОР** (нашей организации) относится документ: по адресату, подразделению, реквизитам.
  2. Получает **перечень дел** номенклатуры этой НОР на текущий год.
  3. Связывает текст документа с **наименованием дела** или с **правилом из промпта**, например «жалобы на ЖКХ → дело 05-12». Правила заказчика важнее совпадения по смыслу.
  4. Отвечает: дело (индекс, заголовок), почему выбрано, 1–2 альтернативы. При неуверенности возвращает в процесс «нужен человек».
- **Навык `nomenclature-match`:** нормализует заголовки дел, применяет правила заказчика, затем ищет смысловое совпадение, ранжирует и объясняет выбор.
- **Новые тулы:**
  - `list_business_units` — НОР;
  - `list_case_files(business_unit, year, department, text)` — дела номенклатуры: индекс, заголовок, подразделение, срок хранения;
  - `place_document_to_case_file(document_id, case_file_id)` — запись; как подтверждается — решить, см. вопросы.
- **Пример агента:** «делопроизводитель» в Aura (npo-comp, тип 7197cc31…).

### 3.2. Поиск подобных обращений

- **Вход:**
  - промпт, в котором обязательно **период**;
  - **ФИО** — с похожими вариантами по справочнику **Персоны**;
  - **вопрос** — найденный классификатором или заданный кодом.
- **Поиск:** по ФИО, вопросу и глубине (период и уровень классификатора: вопрос → тема → тематика).
- **Ответ:** список ссылок на обращения, у каждого — дата, вопрос и совпадение («то же лицо», «тот же вопрос», «оба»).
- **Период:** проверить, отдаёт ли RX период повторности из настроек организации. Если нет — параметр тула со значением по умолчанию 180 дней (как в `og-repeat`).
- **Новые тулы:**
  - `search_persons(fio, fuzzy)` — справочник Персоны: похожие ФИО, дата рождения или адрес для различения однофамильцев (без вывода ПДн);
  - `find_similar_citizen_requests(person_ids | fio, question_code, depth, date_from, date_to)` — обращения со ссылками.
- **Навык:** расширить `og-repeat` режимом «поиск подобных» — тот же скрипт сравнения, вход шире.
- **Приоритет — P1:** дёшево (два тула чтения), частый вопрос, прямо требуется ст. 11 59-ФЗ.

### 3.3. Полная маршрутизация — агент «Маршрутизатор»

- **Правила:** получаем обратную связь от заказчика. Без них агент только предлагает маршрут, сам его не выбирает.
- **Навыки:**
  - **Рассмотрение** — проект резолюции, адресат по вопросу, своя НОР. Основа — `kd-resolution`, то есть история резолюций руководителя, плюс правила заказчика.
  - **Исполнение** — задача на исполнение и сопроводительное письмо.
  - **В дело** — документ автоматически помещается в дело и меняет статус; нужен тул записи (см. 3.1).
  - **Определение вида маршрута (ВУ)** и **предполагаемых исполнителей** по задачам.
- **Открыто:**
  - **Проект резолюции:** готовить его в задаче на рассмотрение — как текст в задании или как черновик поручений?
  - **Перенаправление:** определять исполнителя через прикладную разработку RX или в агенте?
  - **Доска:** пункта ещё нет на доске — завести.

## 6. Вопросы к RX и к заказчику

1. **Номенклатура:** сущность дел и её поля (индекс, заголовок, подразделение, год, срок хранения). Как документ помещается в дело: свойство документа или отдельная операция? Что меняется в статусе «в дело»?
2. **Персоны:**
   - как обращение связано с персоной-заявителем;
   - можно ли фильтровать обращения по персоне и коду вопроса;
   - где лежит период повторности.
3. **Маршрутизация:**
   - где у заказчика хранятся правила «вопрос/вид/корреспондент → адресат/исполнитель»;
   - есть ли справочник в решении;
   - как штатно создаётся задача на рассмотрение и на исполнение.
4. **Вызов Cowork из процесса RX:** что передаёт блок процесса (id документа, id задачи)? Можно ли взять пример агента «делопроизводитель» из Aura?
5. **Запись «в дело» без подтверждения человека:** допустима ли, как `doc-version`, или только после «да»?

## 7. Ответы по RX (сессия «Установка Product Assistant», 20.11.2026)

Источники: справка RX 26.3 и исходники базового RX. Пометка «проверить» означает, что ответ не подтверждён: имя набора OData или поведение надо сверить на стенде через `odata_describe_entity`.

### Номенклатура дел

- **Сущность.** Дела номенклатуры — справочник `Sungero.Docflow.CaseFile`, в OData предположительно `ICaseFiles` — проверить.
- **Поля дела:**
  - `Index` — индекс, уникален в рамках НОР и периода;
  - `Title` — заголовок;
  - `Department` — подразделение, обязательно, только если дела ведутся в разрезе подразделений;
  - `RetentionPeriod` — срок хранения;
  - `StartDate`, `EndDate` — период дела;
  - `Year` — год; у переходящих дел (`LongTerm`) пуст;
  - ещё: `BusinessUnit` (НОР), `RegistrationGroup`, `Responsible`.
- **«В дело» — это заполнение свойства документа, отдельного статуса нет.** Пишется `OfficialDocument.CaseFile`. `PlacedToCaseFileDate` RX ставит сам. Если у заказчика «в дело» — это блок процесса или результат задания, это прикладная доработка.
- **Дело по умолчанию.** Подсказки есть только в персональных настройках регистратора: `IncomingCaseFile`, `OutgoingCaseFile`, `InnerCaseFile`. Связей «вид документа → дело» и «подразделение → дело» в базовом RX нет. **Правила подбора дела хранит агент** — в навыке `nomenclature-match` или в конфиге заказчика.
- **Что меняется в тулах:**
  - `list_case_files(business_unit, year, department, text)` — поверх `CaseFiles`; переходящие дела берутся независимо от года;
  - `place_document_to_case_file` — запись `CaseFile` у документа;
  - НОР — `BusinessUnit` у дела и у документа.

### Персоны и подобные обращения

- **Персоны.** `Sungero.Parties.Person` — наследник `Counterparty`, репозиторий `People`. В OData — `IPeople` или `ICounterparties` с фильтром по типу; проверить.
- **Поля персоны:** `LastName`, `FirstName`, `MiddleName`, `DateOfBirth` и др. Телефон, адрес, email и СНИЛС **наружу не отдаём** — правило mcpOGV.
- **Заявитель обращения** указан в `Correspondent` входящего документа. Штатный поиск «Документы по контрагенту» = фильтр `Correspondent/Id`.
- **Обращение гражданина как тип** есть не в базовом RX, а в решении «Обращения граждан» на стенде: на нём уже работают `get_citizen_request_status` и `list_citizen_requests_due`. Классификатор, признак «Повторное» и период повторности берутся оттуда.
- **Штатного поиска подобных нет.** Возможная основа для поиска по смыслу — модуль `QASearchCore` (RAG); проверить, что он отдаёт.
- **Что меняется в тулах:**
  - `search_persons` — по `People` / `Counterparties`, похожие ФИО плюс дата рождения для различения однофамильцев;
  - `find_similar_citizen_requests` — поверх сущности обращения решения: фильтр по `Correspondent` (найденные персоны), коду вопроса и уровню классификатора, период.

### Маршрутизация и проект резолюции

- **Справочника правил маршрутизации в базовом RX нет.** Адресат берётся из поля `Addressee` / `Addressees` входящего. Вариант — правила согласования с этапом «Рассмотрение адресатом» или условия no-code-процесса. **Правила «вид / корреспондент / тема → кто рассматривает» хранит агент** (`get_routing_rules` читает файл правил навыка) или прикладная доработка.
- **Рассмотрение — `DocumentReviewTask`:**
  - поля: `Addressee`, `Addressees`, `Deadline`, `ResolutionText`;
  - группы вложений: «Документ на рассмотрение», «Приложения», «Проект резолюции»;
  - входящий перед отправкой должен быть зарегистрирован.
- **Проект резолюции** — черновики `ActionItemExecutionTask` с `IsDraftResolution = true` в группе «Проект резолюции». В работу уходят при результате «Утвердить проект резолюции» / «Отправить на исполнение». Ответ на вопрос «как готовить проект резолюции»: агент кладёт черновики поручений в задачу на рассмотрение, руководитель утверждает одним действием.
- **Штатный ИИ.** Блок `WaitForPrepareDraftResolution` (Ario, «классификация исполнителя») и виртуальный помощник RX Intelligence пишут результат туда же — черновиками поручений. Отдельного поля «рекомендованный адресат» на документе нет.
- **Что меняется в тулах:** `send_document_for_review` дополнить проектом резолюции — черновики поручений `IsDraftResolution` в группу «Проект резолюции». Основа — `kd-resolution` и `create_action_items`.

### Вызов Cowork из процесса RX

- **Штатного блока «вызвать ИИ-агента» нет.**
  - Есть блоки `GenAIProcessing`: вызов LLM по промпту с текстом документа, результат пишется в параметр процесса. Это не агент: без тулов и навыков.
  - Есть `IntegrationAIAgent`: MCP-сервер внутри RX для Directum Smart Agent, направление обратное.
  - Есть `AIAgentContextAction`: запуск агента из карточки или ленты клиента RX.
- **Нужен свой скриптовый блок процесса:**
  - HTTP-вызов Cowork с id документа, id задачи и id блока;
  - затем ожидание результата;
  - образец асинхронного ожидания — `WaitForPrepareDraftResolution`.
- **Агент на нашей стороне** создаёт документы с `task_id`, это уже реализовано, см. `docs/rx-process-cowork-on-behalf-requirements.md`.
- **Примера агента «делопроизводитель» в репозитории Aura нет.** Нужен доступ к его настройке на aura.npo-comp.ru или описание от вас.

### Что осталось открытым

- Проверить на стенде имена наборов OData: `ICaseFiles`, `IPeople`.
- Узнать, что отдаёт наружу `QASearchCore`.
- Получить от заказчика правила маршрутизации и подбора дела.
- Решить, нужно ли подтверждение человека для записи «в дело».
