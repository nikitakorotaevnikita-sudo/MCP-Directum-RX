# Юзкейсы ИИ-ассистента для сотрудников госучреждения — гипотезы

Дата: 2026-09-28. Контур: LibreChat + mcpOGV (MCP-сервер поверх Directum RX). Стенд: `governmentgenai.directum360.ru`.

Документ — рабочий список гипотез для проверки на пилоте. По каждому юзкейсу: кто, в какой ситуации,
что спрашивает в чате, какие инструменты mcpOGV это закрывают, насколько это готово, как понять, что гипотеза
подтвердилась. Приоритизация и план проверки — в конце.

## Как читать

**Формат гипотезы:** «Мы считаем, что *роль* в ситуации *…* сэкономит *…* / перестанет *…*, если сможет спросить
в чате *…*. Подтверждение: *метрика*».

**Готовность:**

| Метка | Значение |
|---|---|
| ✅ Готово | Инструменты есть, проверены на живом стенде |
| 🟡 Частично | Работает, но с оговорками по данным стенда или качеству ответа |
| 🔧 Доработка | Нужен новый инструмент или правка существующего (оценка в днях) |
| ✍️ Запись | Требует создания/изменения данных в RX — этап 5 (preview → confirm), пока не делаем |

**Доступ:** mcpOGV работает с правами пользователя RX. Сейчас на стенде включена сервисная учётка
(Administrator) — для пилота с реальными людьми нужны их собственные логины, иначе «мои задания» и дашборд
будут не их (см. «Риски»).

## Роли

| Роль | Кто это | Главная боль |
|---|---|---|
| **Руководитель** | глава ведомства, заместитель, руководитель департамента | нет быстрой сводной картины: что горит, кто срывает сроки, о чём жалуются граждане |
| **Контролёр** | сотрудник отдела контроля исполнения, помощник руководителя | ручной сбор просрочки по исполнителям, отчёты к планёркам |
| **Специалист по обращениям** | отдел работы с обращениями граждан (59-ФЗ) | сроки ответа, повторные обращения, отчётность по тематикам |
| **Исполнитель** | специалист, получающий поручения и задания | не видит приоритетов, теряет сроки, долго ищет документы |
| **Делопроизводитель** | канцелярия, регистрация входящих/исходящих | поиск документов «по памяти», справки по переписке |
| **Новый сотрудник** | любой, первые недели работы | не знает, как делать типовые операции в RX |

## 1. Руководитель

### UC-01. Утренняя сводка «что горит»
- **Гипотеза.** Руководитель тратит 15–30 минут в день на то, чтобы понять состояние дел через веб-клиент. Одна фраза в чате с ответом за минуту заменит этот обход.
- **Запрос:** «Что у меня горит на сегодня?», «Сводка на утро».
- **Сценарий:**
  1. Свои задания, просроченные и со сроком сегодня.
  2. Выданные поручения со сроком сегодня или на неделе.
  3. Просроченные выданные поручения с исполнителями.
  4. Совещания на сегодня.
- **Инструменты:** `list_my_assignments(only_overdue)`, `list_action_items(outgoing, due=today|week)`, `get_outgoing_action_items_analytics`, `list_my_meetings(days=1)`.
- **Готовность:** ✅ по отдельности. 🔧 Составной тул «сводка дня» (1 день) снизит число вызовов и время ответа.
- **Подтверждение:**
  - ≥ 60 % руководителей пилота открывают чат с этим вопросом ≥ 3 раз в неделю;
  - субъективная экономия ≥ 10 минут в день (опрос).

### UC-02. Кто срывает сроки
- **Гипотеза.** Разбор исполнительской дисциплины к планёрке сейчас готовит помощник вручную, 1–2 часа. Чат сделает то же за 2 минуты с таблицей и ссылками.
- **Запрос:** «Кто из моих подчинённых больше всех просрочил поручения?», «Дисциплина по департаменту за сентябрь».
- **Сценарий:**
  1. Дисциплина по организации и по сотрудникам.
  2. По «худшим» — список просроченных поручений: тема, срок, дни просрочки, ссылка.
- **Инструменты:** `get_discipline_analytics(employee, period)`, `admin_list_employee_action_items(only_overdue)`, `get_action_item(id, entity_type)`.
- **Готовность:** 🟡.
  - Дисциплина считается по одному сотруднику, поэтому таблица по подразделению требует N вызовов: агент делал 20.
  - 🔧 Нужен `get_department_discipline`: разбивка по сотрудникам подразделения одним вызовом, 2 дня.
  - Список чужих поручений сейчас доступен только администратору. Руководителю нужен доступ по оргструктуре (подчинённые), 🔧 3 дня.
- **Подтверждение:**
  - отчёт к планёрке собирается в чате без ручной доработки в ≥ 70 % случаев;
  - ноль «выдуманных» строк: каждое поручение в таблице имеет ссылку на карточку.

### UC-03. Пульс обращений граждан
- **Гипотеза.** Руководитель не видит, о чём сейчас пишут граждане, пока не придёт квартальный отчёт. Регулярный вопрос «о чём жалуются» даст раннее предупреждение о всплесках.
- **Запрос:** «О чём чаще всего пишут граждане в этом месяце?», «Сколько обращений по ЖКХ за квартал и сколько из них разъяснено?».
- **Инструменты:** `get_citizen_requests_analytics(level=topic|theme, period, classifier_code)`, `search_citizen_request_classifier`.
- **Готовность:** ✅. Цифры сверены с `$count` стенда: 1798 обращений, 2174 вопроса.
- **Доработка (идея):** сравнение с прошлым периодом («рост на 40 % по теме “Жилище”»), 🔧 1 день.
- **Подтверждение:**
  - руководитель сам (без аналитика) получает цифры по тематикам;
  - расхождение с официальной отчётностью 0 %.

### UC-04. Подготовка к совещанию
- **Гипотеза.** Перед совещанием руководитель хочет видеть, что было решено в прошлый раз и что не исполнено. Справка в чате сократит подготовку с 20 до 3 минут.
- **Запрос:** «Подготовь меня к завтрашнему совещанию по ЖКХ».
- **Сценарий:**
  1. Совещание и повестка.
  2. Поручения по протоколу прошлого совещания и их статус.
  3. Связанные документы.
- **Инструменты:** `list_my_meetings`, `find_documents(kind=…, text=…)`, `admin_list_employee_action_items` / `list_action_items`.
- **Готовность:** 🔧 `get_meeting_brief` (повестка + протокол + поручения по нему), 3 дня. Нужна разведка связей «совещание → протокол → поручения» на стенде.
- **Подтверждение:** ≥ 50 % совещаний пилотной группы предваряются запросом в чат.

### UC-05. Резолюция по входящему письму
- **Гипотеза.** Руководитель расписывает десятки писем в день. Ассистент, который предлагает текст резолюции, исполнителя и срок по похожим прошлым письмам, ускорит это вдвое.
- **Запрос:** «Что пришло из федеральных органов и ждёт моей резолюции?», «Распиши это письмо Минстрою на 10 рабочих дней».
- **Инструменты:**
  - чтение: `list_letters(incoming)`, `get_document_text`, `add_working_days`;
  - создание: ✍️ `RecordManagement.CreateActionItemExecution`.
- **Готовность:** 🟡 чтение. 🔧 Нужен фильтр «ждёт моего рассмотрения» (задания на рассмотрение). ✍️ Создание поручения — этап 5.
- **Подтверждение:** время от поступления письма до резолюции −30 %; доля резолюций, принятых без правки, ≥ 50 %.

## 2. Контролёр исполнения

### UC-06. Реестр просроченных поручений по исполнителю
- **Гипотеза.** Контролёр ежедневно выгружает просрочку по исполнителям вручную. Чат даст таблицу со ссылками, и выгрузка станет не нужна.
- **Запрос:** «Покажи все просроченные поручения Иванова: тема, срок, на сколько просрочено, кто выдал».
- **Инструменты:** `admin_list_employee_action_items(only_overdue)` → поля `days_overdue`, `author`, `task_id`, `url`; `get_action_item(id, entity_type)`.
- **Готовность:** ✅ под администратором. Проверено: у nadya 55 просроченных, карточки открываются с правильными задачами. Для роли «контролёр» без прав админа 🔧 нужна отдельная роль доступа (1 день, аналог admin gate).
- **Подтверждение:** контролёр не открывает веб-клиент для сбора реестра в ≥ 80 % дней.

### UC-07. Напоминание о сроках на неделю
- **Гипотеза.** Просрочки часто возникают потому, что никто не напомнил за 2–3 дня. Еженедельный список «сроки на неделе по отделу» снизит просрочку.
- **Запрос:** «У кого из отдела срок по поручениям на этой неделе?».
- **Инструменты:** `admin_list_employee_action_items(due=week)` по сотрудникам, `list_action_items(due=week)` для себя.
- **Готовность:** 🟡 для себя готово. По отделу нужно пройти по сотрудникам: 🔧 `due` в `get_department_discipline` / списке по подразделению.
- **Доработка (идея):** плановая рассылка (агент LibreChat по расписанию), зависит от платформы.
- **Подтверждение:** доля поручений, закрытых с опозданием, −15 % за 2 месяца пилота.

### UC-08. Отчёт об исполнении поручения
- **Гипотеза.** По ключевым поручениям руководитель просит «справку о ходе исполнения». Ассистент соберёт её из карточки, отчётов исполнителей и дерева подпоручений.
- **Запрос:** «Подготовь справку о ходе исполнения поручения губернатора №…».
- **Инструменты:** `get_action_item`. 🔧 `get_action_item_tree`: подпоручения, соисполнители, отчёты, 3 дня.
- **Готовность:** 🟡 верхний уровень, без дерева.
- **Подтверждение:** справка принимается руководителем без переписывания в ≥ 60 % случаев.

## 3. Специалист по обращениям граждан

### UC-09. Статус конкретного обращения
- **Гипотеза.** Гражданин звонит и спрашивает о своём обращении. Специалист отвечает за 30 секунд, не открывая карточку и не спрашивая исполнителя.
- **Запрос:** «Что с обращением 13-ОГ?», «Обращения Степановой».
- **Инструменты:** `get_citizen_request_status(registration_number | applicant)`. Готовая фраза: срок, дни до срока, продления, исполнитель, результат по вопросам, письмо-ответ.
- **Готовность:** ✅. Проверено: «На рассмотрении, до срока 23.10.2026 осталось 25 дн., исполнитель Захаров А.А.». Контакты заявителя не возвращаются.
- **Подтверждение:** время ответа на звонок о статусе < 1 минуты в 90 % случаев.

### UC-10. Горящие обращения по 59-ФЗ
- **Гипотеза.** Нарушение 30-дневного срока — прямой риск для ведомства. Ежедневный список «срок в ближайшие 3 дня / уже нарушен» с исполнителями почти уберёт просрочку.
- **Запрос:** «Какие обращения горят на этой неделе?», «Где нарушен срок ответа?».
- **Инструменты:** 🔧 `list_citizen_requests_due` (срок через N дней / просрочено, по исполнителю), 1–2 дня, на базе `citizen_requests` сервиса. `add_working_days` для расчёта сроков.
- **Готовность:** 🔧. Данные есть: `Deadline`, `InitialDeadline`, `ProlongationDeadline` в `IRequests`.
- **Подтверждение:** число обращений с нарушением срока −50 % за квартал пилота.

### UC-11. Повторные и коллективные обращения
- **Гипотеза.** Повторное обращение без связи с предыдущим приводит к противоречивым ответам. Проверка «писал ли раньше и что ответили» перед ответом снизит число жалоб на ответы.
- **Запрос:** «Писала ли Степанова раньше? Что ей отвечали?».
- **Инструменты:**
  - `get_citizen_request_status(applicant)` — список обращений заявителя;
  - `get_document_text` — ответные письма;
  - 🔧 `find_repeated_requests`: тот же заявитель или та же тема, признак `IsRepeated`, ст. 11 59-ФЗ; 2 дня.
- **Готовность:** 🟡 поиск по ФИО готов, связывание — нет.
- **Подтверждение:** специалисты используют проверку перед ответом на ≥ 50 % повторных обращений.

### UC-12. Отчётность по тематическому классификатору
- **Гипотеза.** Ежемесячный и квартальный отчёт по ТОТК собирают вручную из выгрузок. Чат выдаст таблицу по разделам, тематикам и темам с итогами рассмотрения за минуту.
- **Запрос:** «Сколько обращений и вопросов по тематикам за 3 квартал, сколько разъяснено и направлено по компетенции?».
- **Инструменты:** `get_citizen_requests_analytics(level, period, classifier_code)`: обращения и вопросы раздельно, итоги рассмотрения по-русски.
- **Готовность:** ✅. Оговорка по данным стенда: 471 из 1798 обращений без классификации, итог «Не зарегистрировано» — 519 вопросов. Для пилота — на чистых данных.
- **Подтверждение:** цифры совпадают с официальным отчётом 1:1; время подготовки −80 %.

### UC-13. Черновик ответа гражданину
- **Гипотеза.** Типовые ответы (разъяснения) пишутся по шаблону. Черновик на основе обращения, НПА и прошлых ответов по той же теме ТОТК сократит время подготовки ответа вдвое.
- **Запрос:** «Подготовь черновик ответа на обращение 13-ОГ».
- **Инструменты:**
  - `get_citizen_request_status` — обращение;
  - `get_document_text` — прошлые ответы по той же теме, их находит `find_documents`;
  - `ask_documents` — регламенты.
  - ✍️ Создание письма в RX — этап 5.
- **Готовность:** 🟡 черновик в чате возможен. 🔧 Поиск «прошлые ответы по той же теме ТОТК», 2 дня.
- **Подтверждение:** доля черновиков, принятых с минимальной правкой, ≥ 40 %; время подготовки ответа −40 %.

## 4. Исполнитель

### UC-14. Мои задания по приоритету
- **Гипотеза.** Исполнитель начинает день со списка заданий в веб-клиенте и сам сортирует их по срочности. Ответ «что делать в первую очередь» с учётом сроков и важности экономит 10 минут и снижает просрочку.
- **Запрос:** «Что мне сделать сегодня в первую очередь?».
- **Инструменты:** `list_my_assignments(only_overdue)`, `list_action_items(incoming, due=today|week)`, `get_action_item`.
- **Готовность:** ✅. `days_overdue` и срок есть; важность и контроль — 🔧 добавить поля, 0,5 дня.
- **Подтверждение:** ≥ 40 % исполнителей пилота используют запрос ежедневно.

### UC-15. Найти документ «по памяти»
- **Гипотеза.** Сотрудник помнит «письмо из Минфина про дороги, в августе», но не номер. Поиск по признакам с несколькими вариантами и объяснением, почему подошёл, найдёт документ быстрее, чем поиск в веб-клиенте.
- **Запрос:** «Найди письмо из Минфина про ремонт дорог, было в августе».
- **Инструменты:** `find_documents(text, kind, counterparty, period)` → варианты с `match_reasons` и ссылками; ослабление условий, если точного нет.
- **Готовность:** ✅.
- **Подтверждение:** нужный документ в топ-3 в ≥ 70 % запросов; медианное время поиска < 1 минуты.

### UC-16. Пересказ и вопросы по документу
- **Гипотеза.** Длинные письма, приказы и регламенты читают целиком ради пары фактов. Пересказ и точечные вопросы по тексту сократят чтение в 3–5 раз.
- **Запрос:** «О чём этот приказ, какие сроки и кто ответственный?», «Есть ли в письме требование ответить до конкретной даты?».
- **Инструменты:** `find_documents` / `get_document`, `get_document_text` (docx, pdf, txt, PDF-представление).
- **Готовность:** ✅ для документов с текстом. Сканы — 🔧 OCR, отдельная задача.
- **Подтверждение:** пользователь не открывает файл в ≥ 50 % случаев после пересказа; нет жалоб на искажение фактов.

### UC-17. Срок по рабочему календарю
- **Гипотеза.** Сроки «через 10 рабочих дней» и «30 дней по 59-ФЗ» считают в уме и ошибаются на праздниках. Ответ по календарю RX уберёт такие ошибки.
- **Запрос:** «Какая дата будет через 10 рабочих дней от сегодня?».
- **Инструменты:** `add_working_days`. Проверено: +30 рабочих дней от 28.09.2026 → 09.11.2026.
- **Готовность:** ✅.
- **Подтверждение:** ноль ошибок в сроках, посчитанных через чат.

## 5. Делопроизводитель

### UC-18. Реестр переписки с организацией
- **Гипотеза.** Справки «вся переписка с организацией X за год» собирают вручную. Чат выдаст реестр входящих и исходящих со ссылками.
- **Запрос:** «Вся переписка с Минцифры за 2026 год».
- **Инструменты:** `list_documents_by_counterparty`, `find_documents(counterparty, period, kind=incoming_letter|outgoing_letter)`, `list_letters(period)`.
- **Готовность:** ✅.
- **Подтверждение:** справка собирается в чате без ручной выгрузки в ≥ 80 % случаев.

### UC-19. Контроль ответов на входящие
- **Гипотеза.** Часть входящих писем с требованием ответа остаётся без исходящего ответа. Список «входящие без ответа с истекающим сроком» закроет эти дыры.
- **Запрос:** «Какие входящие письма ждут ответа больше 10 дней?».
- **Инструменты:** 🔧 `list_unanswered_letters`: входящие с `ControlGD`/`DeadlineGD` без связанного исходящего (`InResponseTo`), 2 дня.
- **Готовность:** 🔧. Поля есть в `IIncomingLetters` (`DeadlineGD`, `ControlGD`) и `IIncomingDocumentBase` (`InResponseTo`).
- **Подтверждение:** число писем, оставшихся без ответа сверх срока, −50 %.

## 6. Новый сотрудник

### UC-20. «Как сделать в RX…»
- **Гипотеза.** Новички задают коллегам одни и те же вопросы про интерфейс RX. Ответ из справки RX со ссылкой на раздел снимет эту нагрузку с коллег.
- **Запрос:** «Как зарегистрировать входящий документ?», «Как продлить срок поручения?».

## План проверки

1. **Пилотная группа (2 недели):**
   - состав: 2 руководителя, 2 контролёра, 3 специалиста по обращениям, 5 исполнителей;
   - каждый работает под **своей** учёткой RX;
   - включены юзкейсы «Пилот сразу».
2. **Сбор данных:**
   - метрики вызовов mcpOGV (`data/mcp_usage.db`: тул, успех, длительность, обезличенный id);
   - логи диалогов LibreChat с согласия участников;
   - короткий опрос в конце каждой недели.
3. **Критерии по каждому UC** — строка «Подтверждение» выше. Гипотеза подтверждена, если метрика достигнута у большинства участников роли.
4. **Качество ответов:**
   - выборочная проверка 30 диалогов в неделю;
   - «выдуманные» данные (номер, срок, ссылка, которых нет в RX) — блокирующий дефект;
   - пропуски вида `{{уточнить}}` — дефект инструмента или подсказки агенту.
5. **Решение по итогам:** какие UC переводим в продуктивные; какие инструменты из бэклога берём в следующий спринт.

## Риски и условия

- **Сервисная учётка.** Сейчас mcpOGV ходит под Administrator. Для «моих» данных, дашборда (метрики считаются по организации сотрудника; у Administrator нули) и честных прав в пилоте нужны личные учётки.
- **Персональные данные заявителей.**
  - Статус и аналитика обращений не отдают адрес, телефон, email, ПИН.
  - Но `odata_*`, `get_document_text` и ответные письма могут содержать ПДн.
  - Нужна политика по ПДн, до пилота с реальными данными: маскирование и журнал доступа.
- **Память LibreChat.** Memory-агент может сохранить данные из RX в память пользователя. Ограничить `validKeys` и запретить сохранять данные Directum.
- **Качество данных стенда.**
  - Часть обращений без классификации.
  - Демо-данные 2023 года с просрочкой > 1000 дней.
  - У отдельных документов потеряны файлы в хранилище.
  - Цифры на демо-стенде не показательны: пилот — на копии боевых данных.
- **QASearch.** Поиск по регламентам ведомства заработает только после индексации их документов в области поиска RX.
- **Модель и сервинг.** Ошибки `400 unsupported API endpoint` на стороне LibreChat — настройка провайдера модели. Без стабильного tool calling юзкейсы не проверить.
- **Таймауты.** Тяжёлые запросы (аналитика по всем обращениям ≈ 25 с) близки к лимиту LibreChat 60 с. На боевом объёме нужны период по умолчанию или предагрегация.
