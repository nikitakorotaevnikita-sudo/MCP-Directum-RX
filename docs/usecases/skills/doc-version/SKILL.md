# Навык «Новая версия документа» (автономный режим)

Ты создаёшь новую версию документа в Directum RX **сам, без вопроса «Создать?»**. Пользователь или процесс уже
решил, что версия нужна; твоя задача — выполнить это надёжно и отчитаться. Прежние версии RX не трогает: новая
версия добавляется сверху, старые остаются в истории документа.

## Автономный режим: как вызывать тулы записи

Тулы записи mcpOGV двухшаговые. В этом навыке оба шага делаешь подряд, **не останавливаясь на предпросмотре**:

1. Вызов без `confirm_token` → ответ `mode: "preview"`, в нём `will_create` и `confirm_token`.
2. Сразу — тот же тул с **теми же параметрами** и `confirm_token` из шага 1 → `mode: "created"`, `version_id`.

Параметры между шагами не меняй: токен привязан к ним, иначе «параметры изменились» — тогда снова шаг 1.
Пользователю промежуточный предпросмотр не показывай и подтверждения не жди.

**Когда остановиться и не создавать** (единственные случаи, когда работа прерывается):

- тул вернул ошибку — передай её текст пользователю как есть, ничего не выдумывай и не повторяй вслепую;
  в частности «Версии документа … заблокированы» — документ открыт на редактирование или обрабатывается:
  сообщи и предложи повторить позже;
- не ясно, **какой** документ менять (нашлось несколько, нет id) — уточни у пользователя: это не подтверждение,
  а недостающие данные;
- нет содержимого новой версии (пустой текст, нет файла).

`will_create.warnings` (например, «Последняя версия … подписана») — **не повод останавливаться**: создай версию
и передай предупреждение в итоговом ответе.

## Порядок работы

1. **Документ.** Id из запроса или задания; если дано название — `find_documents`. Убедись, что документ один.
2. **Версии.** `list_document_versions(document_id)` — сколько версий, формат последней (`extension`),
   `next_version_number`, `versions_locked`, `last_version_signed`. Если `versions_locked = true` — дальше не иди,
   сообщи (см. выше).
3. **Содержимое** — выбери сценарий (таблица ниже).
4. **Создание** — два вызова подряд (автономный режим). `on_behalf_of` — сотрудник, по чьей просьбе создаётся
   версия (ФИО или id; под служебной учёткой `me` нельзя). `note` передавай **всегда** — см. «Примечание к версии».
5. **Отчёт** — см. «Что ответить».

## Примечание к версии

По примечанию в истории версий RX видно, что версию создал агент, и за кого. Формат — всегда такой:

```
Агент за <Фамилия И. О.>: <что изменилось>
```

- `<Фамилия И. О.>` — тот же сотрудник, что в `on_behalf_of`, в виде «Фамилия И. О.», не id и не логин. Возьми
  ФИО до первого вызова: из `search_employees` или из задания процесса. Если узнал его только из
  `will_create.requested_by.name` предпросмотра — поправь `note` и сделай предпросмотр заново (токен привязан к
  параметрам). Если ФИО неизвестно — спроси, не пиши «пользователь».
- `<что изменилось>` — 3–10 слов по сути: «правки по замечаниям правового управления», «загружен подписанный скан»,
  «текст перенесён из документа 16795».
- Всё примечание — не длиннее 250 символов; если не помещается, сократи вторую часть, а начало «Агент за …» оставь.

Примеры: `Агент за Концева Н. И.: правки по замечаниям юриста`,
`Агент за Иванов И. И.: загружен файл ответа в PDF`.

## Сценарии

| Что нужно | Как | Тул создания |
|---|---|---|
| Исправить текст | `get_document_text` → правка → новый текст (markdown: `#` заголовки, `-` списки, `**жирный**`) | `create_document_body(document_id, text, markdown=true, on_behalf_of, note)` |
| Загрузить готовый файл (до ~1 МБ) | файл в base64 | `create_document_body_base64(document_id, extension, content_base64, on_behalf_of, note)` |
| Загрузить крупный файл | `begin_upload` → `upload_chunk(upload_id, index, chunk_base64)` по порядку → `commit_upload(upload_id, total_chunks)` | `create_document_body_base64(document_id, extension, upload_id, on_behalf_of, note)` |
| Перенести тело из другого документа | `get_doc_body_base64(источник)`; если пришёл `download_id` — `download_chunk` по всем `index`, склеить, `abort_transfer` | как два варианта выше; `extension` — из ответа выгрузки |

Правила по содержимому:

- **Оформление.** `create_document_body` собирает новый `.docx` из текста: бланк, шрифты, таблицы, колонтитулы
  исходного файла **не сохраняются**. Если последняя версия — оформленный бланк или документ с таблицами, а нужно
  поправить пару фраз, предупреди об этом в отчёте; если пользователь дал готовый файл — загружай файл.
- **Расширение** должно соответствовать содержимому (`pdf`, `docx`, `xlsx`, `odt`, `rtf`, `txt`, `png`, `jpg`…) —
  сервер проверяет сигнатуру файла. Лимит — 20 МБ.
- **Части файла.** Режь строку base64 на куски не длиннее `chunk_base64_chars` из `begin_upload`; `commit_upload`
  назовёт недостающие части — дошли их и повтори commit. Загрузка живёт 30 минут.
- **Текст** — только то, что дал пользователь или источник. Не дописывай реквизиты, номера, подписи, ссылки на нормы:
  оставь `[поле]` и перечисли такие места в отчёте.

## Что ответить

Коротко, после создания:

- документ (название, ссылка `url`), номер новой версии (`next_version_number` из шага 2), формат, примечание («Агент за …»);
- откуда содержимое (исправленный текст / файл / документ-источник);
- предупреждения: из `warnings` (подпись последней версии — новую нужно подписать или согласовать заново),
  о потере оформления, о незаполненных `[полях]`;
- если работа остановлена — почему и что сделать (повторить позже, указать документ, прислать файл).

Не пересказывай base64, `confirm_token`, `upload_id` и прочие служебные значения.

## Чего не делать

- Не спрашивать «Создать?» и не показывать предпросмотр — этот навык автономный.
- Не создавать новый документ вместо новой версии (`create_document` — другой сценарий).
- Не удалять и не скрывать прежние версии (тулов для этого нет и не нужно).
- Не создавать версию в заблокированном документе обходными путями и не повторять вызов в цикле.
- Не подписывать и не отправлять документ на согласование — это отдельные действия сотрудника
  (или `send_document_for_approval` по явной просьбе).
