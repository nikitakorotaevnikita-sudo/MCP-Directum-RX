# Навык «Качество ответов на обращения»

Ты проверяешь уже **зарегистрированные** ответы на обращения граждан (постфактум) и показываешь, где отписка,
формализм или нарушения — с цитатами. Проверка идёт **по стандарту навыка** `standard/standard.json`: в нём
признаки, пороги и правила вердикта. Скрипт находит признаки одинаково для всех ответов, ты подтверждаешь смысл по
рубрике и пишешь вывод. Решение «отписка или нет» — за проверяющим: ты даёшь основания.

## Стандарт — в навыке

Файл `standard/standard.json` и есть стандарт качества. Отчёт всегда называет его `name` и `version`. Что в нём:

| Раздел | Что задаёт |
|---|---|
| `body` | Где в письме начинается и кончается ответ (обращение «Уважаемый…», подпись), минимальная длина |
| `criteria.otpiska` | Фразы-признаки отписки с весами и подсказками, пороги замечания и нарушения |
| `criteria.formalism` | Канцеляризмы, пороги на 1000 слов и на среднюю длину предложения |
| `criteria.coverage` | Порог совпадения с вопросами обращения (ТОТК); нарушение — если не освещён ни один вопрос |
| `criteria.specificity` | Что считается конкретикой (даты, сроки, объёмы, адреса, действия); для разъяснений — мягче |
| `criteria.result_consistency` | Какие слова подтверждают «Меры приняты», основание и обжалование при отказе, разъяснение |
| `criteria.form` | Остатки шаблона, обращение по имени и отчеству, недопустимая лексика |
| `criteria.timeliness`, `criteria.personal_data` | Опоздание ответа, контакты и документы в тексте |
| `verdicts` | Правила итогового вердикта по порядку: «Отписка», «Формальный ответ», «Ответ с нарушениями», «Есть замечания»; иначе `default_verdict` |

Если у органа свой стандарт — правят этот файл (фразы — регулярные выражения без учёта регистра; критерий можно
отключить полем `enabled: false`) и меняют `version`. Другой файл стандарта передаётся скрипту параметром
`--standard`. Сам ты стандарт по ходу проверки не меняешь и не подменяешь своими критериями; если пользователь хочет
другие правила — предложи, что поменять в файле.

## Данные

`list_citizen_request_answers(date_from, date_to, prepared_by, classifier_code, limit, skip)` — зарегистрированные
ответы («Ответное письмо») с текстом, обращениями, вопросами ТОТК и результатом по каждому, исполнителем, сроком и
опозданием. Новые первыми, по 5 за вызов (текст читается медленно); `next_skip` — следующая страница.

Без субагентов: собери страницы последовательно (для аудита за месяц обычно 2–6 вызовов) и сохрани ответы тула
**как есть** в один JSON-файл списком страниц. Большой период — предложи сузить (месяц, исполнитель, тематика) или
проверь по частям. Один ответ: `list_citizen_request_answers` за его дату с `prepared_by` или найди номер в списке.

## Скрипт

```bash
python scripts/review_answers.py ответы.json --format md          # отчёт по-русски
python scripts/review_answers.py ответы.json                      # JSON: вердикты, критерии, цитаты, сводки
python scripts/review_answers.py ответы.json --format xlsx-spec > spec.json   # для навыка excel-report
python scripts/review_answers.py ответы.json --standard свой_стандарт.json
```

По каждому ответу: `verdict`, `reasons` (нарушения), `remarks` (замечания), `excerpt` (начало ответа), `criteria`
со статусом (`violation` / `remark` / `ok` / `n/a`), метриками и цитатами `evidence`. Ответ без текста — вердикт
«Нет текста» (файл не получен), он не считается ни хорошим, ни плохим. Сводки: `summary`, `by_prepared_by`,
`by_topic` (код ТОТК до тематики). Коды выхода: 0 / 2 (ошибка данных или стандарта — сообщение в stderr) / 1.

## Рубрика: что подтверждаешь ты

Скрипт ищет признаки; ты читаешь `excerpt` и цитаты ответов с вердиктами «Отписка», «Формальный ответ» и проверяешь
по смыслу (а по «Есть замечания» — выборочно):

1. **По существу ли каждый вопрос.** Есть решение: что сделано или будет сделано, кем и когда, либо почему нельзя и
   что заявитель может сделать. «Рассмотрено», «на контроле», «в установленные сроки» без этого — отписка.
2. **Понятен ли ответ человеку** без юридического образования: нет ли пересказа норм вместо ответа, нет ли
   нагромождения канцеляризмов.
3. **Соответствует ли текст результату** в RX («Меры приняты» — меры названы; «Отказано» — основание и порядок
   обжалования; «Разъяснено» — разъяснение по сути вопроса).
4. **Нет ли небрежности:** остатки шаблона, чужой текст, неподписанное письмо, недопустимые слова.

Если по смыслу ты не согласен со скриптом (например, ответ короткий, но полный) — скажи об этом явно в отчёте
(«признак сработал, но по существу ответ дан, потому что …»). Не придумывай недостатки, которых нет в тексте.

## Как излагать отчёт

1. Итог одной строкой: стандарт (название, версия), период, сколько ответов проверено, сколько с проблемами и доля.
2. Распределение по вердиктам и самые частые нарушения по критериям.
3. Ответы с проблемами — таблица «Ответ (ссылка) — дата — исполнитель — вердикт — почему»; самые показательные
   2–5 примеров с цитатами.
4. По исполнителям и тематикам — где доля проблем выше; без оценки людей, только факты.
5. Что сделать: типовые ошибки и как их исправить (например, убрать остатки шаблона, отвечать на каждый вопрос,
   указывать сроки и меры), для повторяющихся случаев — доработать шаблон письма в RX.
6. Файл — `pdf-report` (справка) или `excel-report` (таблица всех ответов из `--format xlsx-spec`).

В конце — оговорка: проверка по формальным признакам стандарта; окончательный вывод — за проверяющим.

## Правила

- ФИО заявителей и их адреса в отчёт не выноси: ссылайся на номер ответа и обращения. В цитатах, если попалось ФИО
  или контакт заявителя, замени на «[заявитель]».
- Не меняй стандарт молча и не добавляй свои критерии в вердикт; предложения по стандарту — отдельным пунктом.
- Не переписывай ответы целиком без просьбы; для показательного примера — один исправленный абзац (навык
  `og-letters`).
- Это аудит прошлых ответов: в RX ничего не меняешь и не создаёшь.
