# Контроль исполнения без контрольных карт: агент LibreChat + mcpOGV + навыки

Черновик концепции для обсуждения. Исходник — «Проектное решение. Контроль документов (v8)». На стенде
governmentgenai модуля «Контрольное управление» и справочника «Контрольные карты» нет; в Directum RX есть поручения
(задачи и задания на исполнение), признак «На контроле», контролёр (Supervisor), задания контролёру на приёмку
исполнения, сроки и продления.

## 1. Что в проектном решении — архаизм

Проектное решение переносит в RX бумажную контрольную карточку: отдельную запись, куда контролёр вручную
переписывает то, что уже есть в поручениях.

| В проектном решении | Почему это архаизм | Как предлагается |
|---|---|---|
| Контрольная карта — отдельный справочник, «рабочее место контролёра» | Дублирует поручение: исполнитель, срок, текст, связи живут в двух местах и расходятся | Карты нет. Объект контроля — само поручение (дерево поручений) с признаком «На контроле». «Карта» — это **досье**, которое агент собирает из RX на лету, и оно всегда актуально |
| Создание карты из 4 мест (обложка, документ, поручение, задание на постановку) | Четыре входа в одну операцию, риск дублей («откройте существующую или создайте новую») | Один вход: поставить поручение на контроль штатно в RX (флажок, контролёр). Агент находит всё, что на контроле, сам |
| «Вносит вручную изменения, сделанные в поручении, в контрольную карту» | Ручная синхронизация, то есть гарантированное расхождение | Синхронизировать нечего: досье читается из поручения |
| Вкладка «Переносы»: вручную заполнить старый и новый срок, причину; «считает количество переносов и заполняет вручную» | Ручной подсчёт того, что система знает сама | История сроков — из запросов на продление и изменений срока в RX; число переносов и суммарный сдвиг считает скрипт |
| Ежедневный мониторинг: контролёр листает реестр с фильтрами «сегодня / завтра / 3 дня / неделя» | Человек работает фильтром | Агент присылает утреннюю сводку с **прогнозом срыва**, а не только с датами |
| Контроль «по существу» — без поддержки, только комментарий в текстовом поле | Главная работа контролёра остаётся ручной | Навык сверяет отчёт и ответный документ с текстом поручения по пунктам |
| Снятие с контроля: причина и дата в диалоге; делопроизводитель ОИВ «проверяет, что все поручения выполнены» | Ручная проверка условий | Агент проверяет готовность к снятию по чек-листу (все подпоручения выполнены, есть результат, ответ зарегистрирован) и показывает, чего не хватает. Решение и действие — за человеком в RX |
| Поле «Связи» как текст с комментариями и ссылками | Неструктурированный журнал | Комментарии контролёра — в штатной переписке задания или в тексте приёмки; досье собирает их в хронологию |

Главный принцип: **контроль — это взгляд на процесс исполнения, а не отдельный документ**. Всё, что можно
вычислить из workflow, вычисляется; человек принимает решения.

## 2. Архитектура на харнессе LibreChat

```
Контролёр ──► агент «Контроль исполнения» (LibreChat)
                 │  системный промпт: роли, правила, карта навыков
                 ├─ MCP mcpOGV (только чтение): поручения на контроле, досье, история сроков, тексты
                 ├─ навыки kd-*: порядок работы + скрипты (риск, переносы, готовность к снятию, проверка по существу)
                 ├─ субагенты: параллельная проверка «по существу» по исполнителям или пунктам
                 └─ pdf-report / excel-report / pdf-read: справки, выгрузки, чтение присланных отчётов
```

- **Права.** Агент работает под учёткой контролёра: видит то, что видит он. Контрольное управление — роль в RX;
  тулы mcpOGV проверяют доступ так же, как для поручений подчинённых (руководитель — свой периметр, администратор —
  всё). Для контролёров нужна отдельная проверка: входит в роль «Контроль документов» или указан контролёром
  поручения.
- **Состояние.** Агент не хранит собственный реестр. Долговременная память LibreChat — личная и не общая для
  управления, поэтому для данных контроля не подходит; в ней можно хранить только предпочтения контролёра (какой
  периметр, в каком виде сводка).
- **Где нужно своё поле.** Тип контроля и срочность, которые контролёр «устанавливает спец. метками», — это
  единственное, чего нет в поручении. Варианты по нарастанию: (а) штатные поля важности или отметки поручения; (б)
  тег в теме или тексте по соглашению; (в) лёгкое расширение поручения полем «Тип контроля» — без отдельного
  справочника.

## 3. Инструменты mcpOGV

Уже есть и переиспользуются: `list_employee_action_items`, `get_action_item` (с `entity_type` и `task_id`),
`get_department_discipline`, `get_document_text`, `find_documents`, `add_working_days`, `search_employees`,
`get_executive_summary`.

Новые (только чтение):

| Тул | Что возвращает | Замена в проектном решении |
|---|---|---|
| `list_controlled_action_items` | Поручения «На контроле» с фильтрами: контролёр, автор («Выдал»), ответственный исполнитель, соисполнитель, организация-исполнитель, окно срока (сегодня, завтра, 3 дня, неделя, следующая неделя, месяц, период), статус (в работе, снято с контроля, просрочено) | Реестр контрольных карт |
| `get_control_dossier` | Дерево поручения по всем уровням: исполнители, сроки, состояние, просрочки; история сроков; отчёты об исполнении; документы-основания и результаты; ответные письма по связям; переписка | Контрольная карта + вкладки «Исполнение», «Переносы», «Связи» |
| `get_deadline_history` | Все изменения срока поручения и подпоручений: кто, когда, старый и новый срок, причина, одобрено или нет | Вкладка «Переносы» с ручным подсчётом |

Запись — отдельным этапом и только с подтверждением человека: `request_control` (поставить на контроль, назначить
контролёра), `release_from_control` (снять с контроля с причиной). Сначала — только чтение и подсказки «где нажать
в RX».

## 4. Навыки

| Навык | Задача контролёра | Скрипт |
|---|---|---|
| `kd-monitor` | Утренняя сводка: что на контроле, что сорвётся, у кого узкое место | `risk_score.py` — прогноз срыва |
| `kd-dossier` | «Что с поручением?»: досье по всему дереву — кто держит, где просрочка, что сделано | — |
| `kd-extensions` | Переносы: сколько раз и на сколько дней, кто переносит систематически, соответствует ли регламенту | `extension_stats.py` |
| `kd-substance` | Контроль «по существу»: выполнен ли каждый пункт поручения по отчёту и результатам | `match_points.py` — сопоставление пунктов поручения и отчёта |
| `kd-close` | Готовность к снятию с контроля: чего не хватает; черновик причины снятия | `close_readiness.py` |
| `kd-report` | Справка руководителю: исполнительская дисциплина по подразделениям и исполнителям за период | — (данные + `pdf-report` / `excel-report`) |

Скрипты — по контракту остальных навыков: только стандартная библиотека, принимают JSON ответов тулов как есть,
коды выхода 0 / 2 / 1, воспроизводимость через `--today`.

**`risk_score.py` — прогноз срыва вместо фильтра по датам.** Считает для каждого поручения на контроле балл по
прозрачным признакам, каждый со своим объяснением:
- мало времени осталось относительно всего срока (прошло больше 80 % срока, результата нет);
- нет движения: давно нет отчётов, подпоручений, переписки;
- переносы: уже переносилось, особенно больше одного раза;
- просрочены подпоручения нижнего уровня, хотя верхнее ещё в сроке;
- нагрузка исполнителя: много поручений со сроком в ту же неделю;
- исполнитель раньше систематически просрочивал (из `get_department_discipline`).

Вывод: группы «сорвётся», «под угрозой», «в норме» с причинами — контролёр видит, **почему** поручение в группе
риска, и звонит тем, кому нужно, а не всем со сроком «завтра».

**`close_readiness.py` — снятие без ручной проверки.** Проверяет: все подпоручения выполнены; по каждому пункту есть
отчёт или результат; ответное письмо (если нужно) зарегистрировано и отправлено; нет открытых запросов на продление;
срок соблюдён или нарушение отражено. Итог — «готово к снятию» или список недостающего.

**`kd-substance` — главная ценность.** Скрипт делит текст поручения на пункты и находит, какие пункты упомянуты в
отчётах и результатах; агент (или субагенты — по пункту на каждого) читает тексты и оценивает по рубрике «выполнено /
частично / не выполнено / нет данных» с цитатой-доказательством. Это предварительная оценка для контролёра, решение
остаётся за ним.

## 5. Процесс «было → стало»

| Этап | Было (проектное решение) | Стало |
|---|---|---|
| Постановка на контроль | Задание на постановку → кнопка → диалог «есть ли карты» → новая карта → заполнить поля | В RX: поручение «На контроле», контролёр. Агент на вопрос «что нового поставлено на контроль» показывает новые поручения за день и то, что стоит поставить, но не поставлено (по резолюциям руководителя, срочности, внешним документам) |
| Ежедневный мониторинг | Реестр, фильтры по датам | «Утренняя сводка»: риск-группы с причинами, узкие места по исполнителям; файл по запросу |
| Ход исполнения | Вкладка «Исполнение» | «Что с поручением 245?» → досье по дереву |
| Корректировка | Скорректировать в поручении и вручную перенести в карту | Скорректировать в RX; досье обновится само |
| Переносы | Ручной журнал и подсчёт | История из RX, статистика и отклонения от регламента — скриптом |
| По существу | Комментарий в текстовом поле | Сверка пунктов и отчётов с доказательствами |
| Снятие с контроля | Диалог «причина, дата»; делопроизводитель проверяет подпоручения | Чек-лист готовности, черновик причины снятия; действие — человек в RX, позже — тул с подтверждением |
| Отчётность | Нет в проектном решении | Справка руководителю по дисциплине и рискам за период |

## 6. Ограничения харнесса и что проверить

- **Расписание.** Утреннюю сводку агент делает по запросу. Автоматический запуск по расписанию — через внешний
  планировщик (Agents API LibreChat или дайджест, который собирает сервер mcpOGV и отправляет уведомлением);
  возможности текущей версии LibreChat проверить отдельно.
- **Субагенты** нужны для параллельной проверки «по существу» больших поручений; требуют включённой возможности
  субагентов в `librechat.yaml` и настройки агента.
- **Данные стенда.** Нужно проверить на стенде, что доступно по OData: признак «На контроле» и контролёр у задачи на
  исполнение поручения, задания контролёру, история продлений, отчёты. Модуля «Контрольное управление» на стенде нет,
  и он не требуется.
- **Тип контроля и срочность** — решить, какой из вариантов раздела 2 принимаем.
- **Запись в RX** — отдельное решение с безопасностью: сначала только чтение.

## 7. План

1. **MVP (только чтение):** `list_controlled_action_items`, `get_control_dossier`, навыки `kd-monitor`, `kd-dossier`,
   `kd-close`; промпт агента «Контроль исполнения». Демо контролёрам на данных стенда — это закрывает риски 2–3
   проектного решения (не закрыты потребности, не принято пользователями).
2. **По существу и переносы:** `get_deadline_history`, навыки `kd-extensions`, `kd-substance` с субагентами,
   `kd-report`.
3. **Действия:** тулы постановки и снятия с контроля с подтверждением человека; утренняя сводка по расписанию.
