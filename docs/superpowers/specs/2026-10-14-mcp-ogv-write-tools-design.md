# mcpOGV: создание документов и задач (письма, поручения, НПА)

Статус: реализуется. Дата: 14.10.2026.

## Цель

Дать агентам LibreChat создавать в Directum RX: исходящие письма, поручения, проекты правовых актов и правовые
акты, а также запускать типовые задачи по документам (рассмотрение, согласование, простая задача). До сих пор
mcpOGV только читал.

## Главное ограничение: запись идёт от служебной учётки

mcpOGV на стенде работает под Administrator (`service_account=true`). Значит:
- в RX «Автор» (Author) документа и задачи — Administrator, и это не исправить через API;
- поручение, созданное `RecordManagement/CreateActionItemExecution`, по умолчанию «выдал» Administrator;
- документ, созданный администратором, пользователь может не увидеть из-за прав;
- «me» в инструментах — Administrator, а не пользователь чата.

Решения:

| Проблема | Решение |
|---|---|
| Чей это документ или поручение | Обязательный параметр `on_behalf_of` (ФИО или id реального сотрудника) во всех тулах записи; «me» под служебной учёткой — ошибка. Документ: «Подготовил» = он, подразделение и наша организация — из его карточки. Поручение: «Выдал» (AssignedBy) = он. Задача: «Автор» = он (правка черновика до старта) |
| Автор в RX — Administrator | В «Примечание» документа пишется «Подготовлено ИИ-ассистентом (mcpOGV) по запросу: ФИО, ДД.ММ.ГГГГ». Каждая запись — в журнал аудита |
| Пользователь не видит документ | После создания — `Docflow/GrantAccessRightsToDocument` сотруднику `on_behalf_of` с типом прав из настройки `MCP_WRITE_GRANT_RIGHTS_GUID`. Если GUID не задан — права не выдаются, в ответе предупреждение |
| «Выдал» / «Автор» не проставились | Задача создаётся черновиком, правится (PATCH), и только потом запускается (`Docflow/StartTask`). Если правка не удалась — задача **не запускается**, возвращается ссылка на черновик и причина |

## Безопасность записи

1. **Выключатель.** `MCP_WRITE_ENABLED=false` по умолчанию — тулы записи не регистрируются вовсе. На тестовом стенде
   включается в `run.ps1`.
2. **Два шага с токеном подтверждения.** Первый вызов без `confirm_token` ничего не создаёт и возвращает предпросмотр
   (что будет создано: поля по-русски, найденные сотрудники и организации) и `confirm_token`. Второй вызов с теми же
   параметрами и токеном создаёт. Токен — HMAC от параметров, пользователя (отпечаток кредов) и срока; живёт
   10 минут; любой изменённый параметр делает токен недействительным. Агент обязан показать предпросмотр
   пользователю и получить явное «да».
3. **Аудит.** Каждая запись — строка JSON в журнале `mcp_writes.log` (время, тул, обезличенный id пользователя,
   `on_behalf_of`, id созданного, без текста документа).
4. **Без удаления и без изменения чужих документов.** Тулы только создают и запускают новое.

## Тулы

| Тул | Что делает | Через что в RX |
|---|---|---|
| `create_outgoing_letter` | Исходящее письмо: тема, корреспондент (организация по названию или id), подготовил, подписант, в ответ на документ, текст письма → тело docx | POST `IOutgoingLetters`; версия POST `…/Versions`, тело PATCH `…/Versions(id)/Body`; права |
| `create_legal_act` | Проект правового акта или правовой акт: вид, тема, нормативный, подписант, текст → тело docx | POST `ILegalActsLegalDocumentBases` с видом «Проект правового акта» / «Правовой акт» |
| `create_action_item` | Поручение по документу: исполнитель, соисполнитель, срок, текст, контроль и контролёр, выдал = `on_behalf_of`; запуск | `RecordManagement/CreateActionItemExecution` → PATCH `AssignedBy` → `Docflow/StartTask` |
| `send_document_for_review` | Рассмотрение документа руководителем (в том числе с проектом резолюции из навыка `kd-resolution` в тексте) | `RecordManagement/CreateDocumentReviewTask` → PATCH `Author` → `StartTask` |
| `send_document_for_approval` | Согласование документа: подписант, дополнительные согласующие, текст | `Docflow/CreateApprovalTask` → PATCH `Author` → `StartTask` |
| `request_action_item_report` | «Запросить отчёт» по поручению: ответственному — задание дать статус; запрашивать может только выдавший поручение, его контролёр или автор задачи (проверяется в mcpOGV — под служебной учёткой RX не проверит); срок по умолчанию +2 рабочих дня | POST `IStatusReportRequestTasks` (`ParentTask` = поручение, `Assignee`, `MaxDeadline`) → текст POST `…/Texts` → PATCH `Author` → `StartTask`; ответы — в `get_control_dossier.report_requests` |
| `create_task` | Простая задача (задание) исполнителям, с документами во вложении | `Docflow/CreateSimpleTask` → PATCH `Author` → `StartTask` |

Справочники разрешаются по названию: сотрудники — `resolve_employee` (неоднозначность — ошибка со списком),
корреспонденты — `ICounterparties` по вхождению названия (несколько — ошибка со списком), виды документов — по
точному названию.

Тело документа: `body_text` (абзацы через пустую строку) → docx, собранный стандартной библиотекой; до 200 000
символов. Файлы из чата в MVP не принимаются.

## Проверено на стенде

- POST `IOutgoingLetters`: обязательны вид, «Подготовил», подразделение, наша организация, корреспондент — создано
  тестовое письмо id 16800.
- Версия и тело: POST `IOutgoingLetters(id)/Versions` с приложением docx (id 2) + PATCH `…/Body` с `Value` (base64).
- `CreateActionItemExecution` + `StartTask` используется в веб-API проекта (`ActionItemService.create_action_item`).
- Не проверено вживую: создание правового акта, PATCH `AssignedBy` / `Author` у черновика, `CreateApprovalTask`,
  `CreateDocumentReviewTask`, `GrantAccessRightsToDocument` (нужен GUID типа прав). Проверка — после разрешения
  на создание тестовых задач на стенде.

## Вне рамок

Регистрация документов, подписание, отправка корреспондентам, удаление и изменение существующих документов.
